# Interface

The workbench draws every control and surface from its own component layer in `web/src/ui/kit/`. Behavior comes from Base UI; each component is a `.tsx` file with, when it draws anything, a `.css` file whose classes start with `ui-`, and the CSS reads its type sizes, colors, radii, elevations and motion from the tokens in `web/src/styles/app.css` (a component's own geometry, such as a control's height, is written in its CSS). A few modules without markup (`floating.ts`, `refs.ts`, `mediaQuery.ts`, `clientValue.ts`, `motionToken.ts`, `dialogPresence.tsx`, `popupHandle.ts`) are shared by the components. Component styles sit in the `components` cascade layer, so utility classes passed by a caller override them.

## Tokens and the page environment

`app.css` defines the only colors, type sizes, radii, elevations, durations, easing curves, breakpoints and stacking steps that exist; Tailwind's stock palette, type scale, radii, shadows, easings, breakpoints and animations are cleared. Colors are named by role: `fg` for text, `canvas`, `container` and `elevated` for the three backgrounds, `fill` laid over a background, `border`, `primary`, the four status colors, and the two brand greens of the logo tile. The dark scheme redefines the same variables under the `dark` class, which follows the system preference and is set before the first paint; when the reader changes the scheme, transitions are held for a frame so the whole page turns at once. Fonts are the system stack.

The base layer is part of the design: components assume its resets (form controls inherit only family, size and line height; buttons keep their default padding; svg stays inline), the unitless body line height, and the focus ring on elements no component owns. A component whose look depends on the environment is fixed there, not with an override at its call site.

Code outside the kit uses semantic utilities (`text-fg-secondary`, `bg-fill-tertiary`, `border-border`) and never raw colors; secondary text is `text-fg-secondary` on the element that holds it. Drawings on the image canvas read the same variables (`var(--color-success)`), so marks follow the scheme, and series and treatments take `--color-chart-1` to `--color-chart-8` in order. Annotation class colors are the one exception: they are part of a model's data (`web/src/domain/models/classes.ts`), shared with server-side rendering and exports, so they are stored as hex values rather than tokens. Token names are always written out in full, never assembled from a variable, so a search for a token finds every use. `web/test/tokens.test.ts` holds the tokens to this: each is read somewhere, each variable read is declared, each color has its dark value, and no name is assembled.

Two widths change the layout: `--breakpoint-mobile` and `--breakpoint-laptop`. Stylesheets use both through Tailwind's variants; scripts read `--breakpoint-laptop` through `useIsCompact` (`web/src/ui/kit/mediaQuery.ts`), so the two never disagree.

## Pages

The signed-in frame is `Shell` (`web/src/ui/shell/Shell.tsx`). The sidebar sits on the canvas: its top row is the signed-in person (`Avatar`, name, chevron; the menu leads to settings and signs out) and the toggle; then the places as 36px rows (experiments, where researchers work, and models, where a model is kept accurate: its versions, datasets and training runs all live on the model's page) and, under them, the experiments as a folding group (`AppNavGroup`: a 12px heading with the count, 16px icons), each one a place of its own; at the bottom the color scheme menu at the row's end; settings are reached from the person's menu. While a settings page is open the person and the places give way to a trail back home and the settings section. The sidebar is a `DraggablePanel` on the left, 240px wide and dragged at its seam up to 400px; Mod+B folds it away entirely, its toggle moving to the start of the top bar, and a cookie the server reads remembers the choice. Its toggle and the person's chevron take no room until the pointer or focus is in the sidebar, and a folding group closes over its rows as they fade. The page sits in one card with a full-strength border and no shadow. Its 44px top bar shows only when it has something to hold: the sidebar's toggle while the sidebar is hidden; on any page below the top level the way back up (`ShellTrail`), a breadcrumb taken from the route's crumbs whose last crumb is the page itself, followed on a workbench by its subject's status; and a workbench's commands (`ShellActions`). A top-level page has no bar: the sidebar's highlight already says where the reader is. Pages outside it, sign-in and consent, sit in `AuthLayout`: one bordered surface inset from the viewport with the mark on its green tile (`LogoTile`) at the top, the language and color scheme menus at the bottom and the content bare in the middle. Sign-in takes two steps, the email and then the password under the email it is for; its fields are named by their placeholders and icons, their labels kept for assistive technology. Crumbs come from each route's `staticData.crumbs` (`useCrumbs`); on a phone the bar names only the page. The browser tab is named in the route's `head` by `documentTitle` (`web/src/ui/documentTitle.ts`), from the page's name or, for a page inside another, one parameterised message naming both.

A page is one of three kinds, chosen by what it holds: a document (`Page`) for the experiments, models and training sets a researcher reads and works through, a workbench (`Workbench`) for one photograph framed and edited, and a settings page (`SettingsPage`) for the reader's own account and the workspace's people and machines. Each kind has one frame, and every page of a kind is assembled the same way. The kinds differ where their content does, in width and arrangement, and are built from the same parts so they read as one product: one page title, `PageHeader` (24px at 600, the page's `status` right after it, a line of `description` or of `meta` facts at 13px tertiary, the page's commands at its end: at most one primary button, then a `PageMenu`; a page about one thing leads it with its `icon` on the 40px tile its card carries in the list); one section heading, `SectionHeader` (16px at 600 with an `extra` at the row's end for a count or a small default button, never a primary one; `compact`, 12px at 600 tertiary, in a side panel or for a group inside a section); one lead figure, `StatisticHero` (the value large on a band of fill over its title and facts, its progress as a `ProgressMeter` or a chart at the band's end; `compact` in a side panel); one list of facts, `Descriptions` (labels in a column, values after them); one empty place, `EmptyPlace` holding an `Empty`; and one right-hand panel, `SidePanel`, for whatever stands beside the main content: 360px, resized from 300 to 600 at its seam and folded from the page that holds it, its content stacked 16px apart in a padded column that scrolls on its own, and a drawer on narrow screens. A panel showing something the reader chose (a preview) is `dismissible`, its title and a close button over the content; one that stays (an inspector) is named for assistive technology only.

`Page` (`web/src/ui/Page.tsx`) is a document across the card's full width, padded 24px above and 32px at the sides (16px on a phone), its parts stacked 24px apart in a fixed order: the `PageHeader`; at most one `StatisticHero`, the figure the page leads with; then its `PageSection`s, each a `SectionHeader` over one surface. Every block of content sits in a titled section, and a section with nothing to show keeps its heading over an `EmptyPlace`. Parts of one subject that a reader works in one at a time are `Tabs` instead of stacked sections: the tabs name the parts, the part on show follows them, and the address keeps the tab on show. A list page is a header with a description over its list, the experiments in a `Table` and the models in a `CardGrid`; a page about one thing sets `icon`, `status` and `meta`. A training set leads with how many of its images are reviewed and so can train, its size and what has been reviewed since its last run beside the title; a training run with its best score and its epochs' progress. An experiment is two tabs: its units first, a row each with the treatment it belongs to and its count on each observation day, filtered by treatment; then its treatments, a row each with its factor, note and number of units, and a new treatment added from the table's toolbar. A page whose rows are worth a look before they are opened passes `preview`: a row's name then links to the same page with the row named in the search, and the row shows in a dismissible `SidePanel` at the card's end (`PreviewLayout`) with `PreviewMedia` and `Descriptions` over one primary command that opens it in full; the page fills the card and scrolls in its own column.

`Workbench` (`web/src/ui/shell/Workbench.tsx`) is built around one framed subject and fills the card edge to edge: the subject on the left with the controls that act on it floating over its top edge (`WorkbenchToolbar`), the way to the subjects beside it in a 44px bar under it (`WorkbenchFooter`), and facts in a resizable inspector on the right (`WorkbenchInspector`, in the `SidePanel`), folded away and brought back by the last command in the top bar, which on narrow screens opens its drawer. It has no header of its own; the top bar stands for one, its trail ending in the subject with the subject's status after it (`WorkbenchStatus`) and its commands at the bar's end. The inspector is a column of `WorkbenchSection`s, each under a compact `SectionHeader` and ruled off from the next: first the figure the subject gives on a compact `StatisticHero`, which names itself, and its details last as `Descriptions`. It floats a lasting state over the subject with `WorkbenchAlert` and an empty subject with `WorkbenchEmpty`. The frame outlives its subject: a step to the subject beside it (`useStep`, `web/src/ui/hooks/useStep.ts`) keeps the page on view until the next one's data and the previews of its pictures are on hand and then replaces what the slots hold, so the frame, the inspector's width and the footer stay in place and no step passes through an empty frame; the subjects an arrow key leads to are fetched while the current one is read, and a wait long enough to notice dims the picture. A unit's workbench can also set two of the unit's days side by side (`DayComparison`, `web/src/features/experiments/DayComparison.tsx`), turned on and off by the last control of its footer or by C and kept in the address (`compare`): the reference day on the left and the day in view on the right, one above the other on a phone, each named and chosen by a `Select` over its corner in place of the footer's days. An `ImageViewport` holds its view relative to its image (how far past filling the frame, and which point of the image is at the center), so two viewports given one `link` show the same part of the dish whichever is zoomed or panned. The comparison is for reading: no boxes and no review command; its inspector keeps the unit's culture status and treatment. A step to another unit keeps both days, waits for both previews, and starts the view afresh.

`SettingsPage` (`web/src/ui/Page.tsx`) is a centered column at most 1024px wide, since what it holds is short and read row by row: its `PageHeader` with the page's one command, ruled off from the content, then `SettingsGroup`s 36px apart, or for a page that is one roster (users, machines) the roster's `Table` itself. A group is a fill tray holding its `SectionHeader` and a bordered panel of `SettingsRow`s (label and description on the left, the control in a column at least 240px or a third of the row wide), `SettingsValueRow`s for facts about the reader (label in a 160px column, the value after it, an action at the end), or a table. Pages declare what they contain; they do not write layout for the frame.

A figure answers a question about the subject; the state an item is in while it is processed (waiting, read, failed) shows on the item itself and is never totalled into a figure. A few things a reader opens one at a time (models, a model's training sets) are `SummaryCard`s in a `CardGrid`: an `IconTile`, the name over its facts and an arrow, and `SummaryCardStats` of its size at the foot. Things a reader scans, searches and compares by their attributes, or keeps in place (experiments, versions, runs, images, units, people, keys, machines), are a `Table`. The experiments table answers what each one grows (material, explant, base medium), when it was inoculated, the size of its design and how far its observations have come (their number and the date of the last one), with a search over the names, materials and media; results belong to the experiment's own page, not to the list.

Surfaces on a page are a thin border on the container color, radius 12, or a band of fill when they must weigh more; a settings group is a fill tray holding a bordered panel. Shadows belong to what floats over the page. A `Table` draws its own outlined card: its header band runs to the card's edges with its first and last columns inset 16px and a hairline between rows. Content that is neither a table nor cards, such as a chart or a run's parameters, sits on a `Card`, the same outline padded 20px. A long table holds its search and filters in a `toolbar` band above the header (a small `Input` 192px wide and an outlined `ToggleGroup`), and its `Pagination` in a `footer` band under the last row, 20 rows to a page. A table whose rows are added in place, on a page with a command of its own, holds its small add `Button` in the `toolbar`. Inside a surface that already frames them, a settings group, tables drop the card (`Table variant="borderless"`): the header band or hover fill then reaches the surface's edges through `--surface-gutter` and insets its text by the same amount; each padded surface sets the gutter to its own padding.

A link starts loading its page when the pointer rests on it or focus reaches it, so most clicks land on data already fetched. A route still loading 200ms after the click shows `pendingComponent` in the shape the page will take, which leaves as soon as the data arrives, built from the skeleton parts next to what they stand for: `PageSkeleton` and its parts in the kit (`PageHeaderSkeleton` with the `icon`, `description` and `meta` the header shows, `StatisticHeroSkeleton`, `TabsSkeleton`, `TableSkeleton`, `CardGridSkeleton`, `SettingsGroupSkeleton`), `PageSectionSkeleton`, `SettingsPageSkeleton`, `PageColumnSkeleton` (the page's column, with `PageHeaderSkeleton` first), `WorkbenchSkeleton` (the subject's frame filled edge to edge over the footer's bar, with a `StepperSkeleton` in it and the inspector's sections as its children: `WorkbenchSectionSkeleton`, `StatisticHeroSkeleton`, `DescriptionsSkeleton`), and a feature's own (`ImageWorkbenchSkeleton`, `UnitWorkbenchSkeleton`, `EpochChartsSkeleton`) beside its component. A skeleton holds the regions the page will hold, each where and as large as it will be, and nothing the page will not have. Skeletons are sized by the type scale and the components they imitate, never by pixels in a route. A page that reloads its data on a timer (`useRouteRefresh`) skips a tick while the router is loading, so a slow way to another page is never begun again. A page left in a hidden tab for five minutes or more reloads its data when the reader returns to it. A write reads its page's data again when it finishes (`router.invalidate()`); a write that takes the reader to another page goes there through `useNavigateAfterWrite`, which also reads again what stays on screen, such as the navigation's experiments, so the shell never shows the workspace as it was before the write.

## Composition

Controls and surfaces come from the kit. A feature never imitates one with `rounded-*`, `border`, `bg-*` and `shadow-*` utilities, and never overrides a component's internal height, radius or padding; it chooses a `size`, `variant` or `type`. Width, position and visibility belong to the outer layout. A missing component is added to the kit, not drawn in a route. `bun run architecture:check` rejects, outside the kit, type utilities (`text-xs`, `text-fg-*`, `font-medium`), stock breakpoints, `rounded-*` and `shadow-*`, raw lengths and colors in classes, and inline styles anywhere but the image viewport's drawings.

Things of the same kind look the same, and things of different kinds look different; the difference is carried by shape before color or size. One fact has one control: a status and the actions it allows are one menu, not a tag beside a row of buttons. A state is a `Status`, its mark and its word, and in a table it has a column of its own; `StatusDot`, the mark alone with the word on hover, only sits right after a name. A mark whose tone changes while it is on the page springs in anew, so a change is seen where it happened; one that arrives with the page is still. An attribute, such as a key's scope or a model's kind, is a `Tag`. A selection of one value is a `Select`, or a `ToggleGroup` when the few options should stay visible, its fill sliding from the last selection to the next; a toggle is a `Switch`; a command is a `Button`. A list is for finding a thing: the name links to its page, and the thing's actions live on that page. An icon tile marks the kind of thing a card or page stands for, the same icon the sidebar gives that kind; the only avatar is the signed-in person's, their initials on a square. A dense data grid takes `Table size="small"`. A row with one action shows it as an `ActionIcon` with a `title`; a row with several gathers them in `RowMenu`, and a page or workbench puts its secondary actions in `PageMenu` (both in `web/src/ui/ActionsMenu.tsx`). Row actions sit in the table's `actions` cell and show while the row is hovered or focused, or while a command of the row's menu is running, when the menu's dots give way to a turning ring (`RowMenu busy`). A name is set in the sans-serif at 500. Figures are sans-serif with tabular digits; monospaced type is only for code, keys and addresses. Text takes three colors: names and values in the text color, a table's cells included; a description under a name secondary; a page header's metadata and placeholders tertiary. A lighter color in a value says something about it, such as a count nobody has reviewed yet. Outside the kit, type is set only through `Text` (its `size` on the type scale, `type` for the color and `weight`); a `Timestamp` and a `Day` take the color of where they stand. An instant (`Timestamp`) reads on the reader's own clock, written in UTC with the zone named until the page hydrates; a calendar day (`Day`), such as an observation day, never moves with the zone. Menu items that open a dialog or ask for confirmation end with "…"; one that downloads a file is a link (`href`). An icon-only control is named by its `title`, which is also its tooltip, or by `aria-label` when it has no tooltip — never both. Tooltips share one popup, so after the first has opened the next shows without the delay; controls that stand together, in the sidebar, the top bar or a `Toolbar`, sit in a `TooltipGroup`, where the popup glides from one to the next. A name cut to one line with an ellipsis, in the sidebar, the breadcrumb or a card, shows whole in an `OverflowTooltip` while it is cut. A value that does not exist yet is drawn as `Absent`.

A success toast confirms a command whose result is not visible where the reader is: a removal, a revocation, a sign-out elsewhere, work started in the background. A creation or edit that appears in place needs no toast. Every failure is a toast, raised by `useAsyncAction` or, for work outside an action, by `runAction` (`web/src/ui/hooks/useAsyncAction.ts`). A state that lasts while the page is open is an `Alert`. A failure written on the page states the conclusion and the way out (Retry); the raw error goes in the `Alert`'s `detail`, folded away and copyable. An empty region is an `Empty` that says what is missing and offers one way forward: a command on the same page is a primary `Button`, and a way to another page is a default `Button` rendered as the link (`render`), never a bare text link. An empty table or list is replaced whole by its `empty`, header and all, on a dashed band of fill where its card would be (under a `toolbar`, a filter that matches nothing shows its `empty` inside the card, so the filters stay), and while it is empty the page or group does not offer the same command in its header. A loading region keeps its final shape. Irreversible actions ask first with `confirmDestructive`.

A dialog that collects input is a `FormDialog` (`web/src/ui/FormDialog.tsx`). The caller owns its trigger and `open` state; the feature's dialog holds its `useAsyncAction` and passes `busy`, and while busy the dialog cannot be dismissed. The form inside mounts with each opening and so starts fresh. A dialog whose footer reads state of its own renders inside a `DialogSession`, and one that starts work as soon as a file is dropped has no footer. A secret shown once after it is created appears in `RevealOnceDialog`, its values as `CopyableCode`, the read-only code block a copyable value takes inside a dialog; on a settings page such a value is a `SettingsValueRow` whose action is a `CopyButton`. Dialogs come in two widths, `default` (520px) for a form in one column and `wide` (640px) for a table or a design laid out in two columns. Fields stack 16px apart; only a pair of short fields (a date and a number) shares a row, and related fields gather into a `Form.Group`, whose heading (14px, 600, ruled off from the fields) is the one way a dialog titles a section. Small descriptions under a field or link exist only when they change what the reader does or prevent a mistake; text that restates a label is left out.

All copy goes through Paraglide, including the kit's default labels, which live in `web/messages/ui/`. Messages are split by module (`web/messages/<module>/`), and a value joined with other text is one parameterised message, never fragments and punctuation put together in JSX. Messages speak in product words; `web/test/product-words.test.ts` keeps code identifiers out of them. Values are written in the current locale by one helper each: lists of like things with `formatList` (`web/src/ui/lists.ts`), numbers with `web/src/ui/numbers.ts` (counts, fixed decimals, percents), numbers inside a message by the message itself (a `number` declaration, never a pre-formatted string), calendar days with `Day` and instants with `Timestamp` (`web/src/ui/Day.tsx`, `web/src/ui/Timestamp.tsx`).

## Adding or changing a component

A new component follows the same shape: a small set of props, styles block by block in its CSS, motion through the easing and duration tokens (under reduced motion everything finishes at once except a turning ring, which still has to say that work is under way), and an implementation that renders the same markup on the server and in the first client frame. It exposes only what the workbench uses.

A change to the interface is done when it passes `make check-web`; when it has been looked at in the light and dark schemes and at mobile width; and when every region it adds shows its pending, empty and error states where they apply.
