# Interface

The workbench draws every control and surface from its own component layer in `web/src/ui/kit/`. Behavior comes from Base UI; each component is a `.tsx` file with, when it draws anything, a `.css` file whose classes start with `ui-`, and the CSS reads its type sizes, colors, radii, elevations and motion from the tokens in `web/src/styles/app.css` (a component's own geometry, such as a control's height, is written in its CSS). A few modules without markup (`floating.ts`, `mediaQuery.ts`, `motionToken.ts`, `dialogPresence.tsx`) are shared by the components. Component styles sit in the `components` cascade layer, so utility classes passed by a caller override them. There is no second component library and no theme runtime.

## Tokens and the page environment

`app.css` defines the only colors, type sizes, radii, elevations, durations, easing curves, breakpoints and stacking steps that exist; Tailwind's stock palette, type scale, radii, shadows and easings are cleared. Colors are named by role (`fg` for text, `canvas`, `container` and `elevated` for the three backgrounds, `fill` laid over a background, `border`, `primary`, and the four status colors) and the dark scheme overrides the same variables under `.dark`. The `dark` class on `<html>` follows the system preference; an inline script in `__root.tsx` sets it before the first paint. Fonts are the system stack.

The base layer is part of the design: components assume its resets (form controls inherit only family, size and line height; buttons keep their default padding; svg stays inline), the unitless body line height, and the focus ring on elements no component owns. A component whose look depends on the environment is fixed there, not with an override at its call site.

Code outside the kit uses semantic utilities (`text-fg-secondary`, `bg-fill-tertiary`, `border-border`) and never raw colors; secondary text is `text-fg-secondary` on the element that holds it. Drawings on the image canvas read the same variables (`var(--color-success)`), so marks follow the scheme, and series and treatments take `--color-chart-1` to `--color-chart-8` in order. Annotation class colors are the one exception: they are part of a model's data (`web/src/domain/models/classes.ts`), shared with server-side rendering and exports, so they are stored as hex values rather than tokens. Token names are always written out in full, never assembled from a variable, so a search for a token finds every use. `web/test/tokens.test.ts` holds the tokens to this: each is read somewhere, each variable read is declared, each color has its dark value, and no name is assembled.

Two widths change the layout: `--breakpoint-mobile` and `--breakpoint-laptop`. Stylesheets use both through Tailwind's variants; scripts read `--breakpoint-laptop` through `useIsCompact` (`web/src/ui/kit/mediaQuery.ts`), so the two never disagree.

## Pages

The signed-in frame is `Shell` (`web/src/ui/shell/shell.tsx`): navigation on the canvas, collapsible to an icon rail with Mod+B and remembered in a cookie the server reads, and the page in one card whose top bar holds the breadcrumb and, on a workbench, its actions (`ShellActions`). Breadcrumbs come from each route's `staticData.crumbs`, after the label of the navigation group the page belongs to. The browser tab is named in the route's `head` by `documentTitle` (`web/src/ui/documentTitle.ts`), from the page's name or, for a page inside another, one parameterised message naming both.

A page is one of two kinds. `Page` (`web/src/ui/Page.tsx`) is a document: a `PageHeader` with the title, an optional description and the page's actions, then sections, tables and cards in the card's padded, scrolling content. `Workbench` (`web/src/ui/shell/Workbench.tsx`) is built around one framed subject and fills the card edge to edge: the subject on the left with its toolbars floating over it (`WorkbenchToolbar`), facts and display controls in a resizable inspector on the right (`WorkbenchInspector`), which becomes a drawer on narrow screens. A document page groups its content with `PageSection`; a workbench groups its inspector with `WorkbenchSection`, and floats a lasting state over the subject with `WorkbenchAlert` and an empty subject with `WorkbenchEmpty`. Pages declare what they contain; they do not write layout for the frame. A route with a loader shows `pendingComponent` in the shape the page will take, built from the skeleton parts next to what they stand for: `PageSkeleton` and its parts in the kit, `PageSectionSkeleton`, `WorkbenchSkeleton`, and a feature's own (`EpochChartsSkeleton`) beside its component. Skeletons are sized by the type scale and the components they imitate, never by pixels in a route.

## Composition

Controls and surfaces come from the kit. A feature never imitates one with `rounded-*`, `border`, `bg-*` and `shadow-*` utilities, and never overrides a component's internal height, radius or padding; it chooses a `size`, `variant` or `type`. Width, position and visibility belong to the outer layout. A missing component is added to the kit, not drawn in a route. `bun run architecture:check` rejects, outside the kit, stock breakpoints, `rounded-*` and `shadow-*`, raw lengths and colors in classes, and inline styles anywhere but the image viewport's drawings.

Things of the same kind look the same, and things of different kinds look different; the difference is carried by shape before color or size. One fact has one control: a status and the actions it allows are one menu, not a tag beside a row of buttons. A selection of one value is a `Select`, or a `ToggleGroup` when the few options should stay visible; a toggle is a `Switch`; a command is a `Button`. A row with one action shows it as an `ActionIcon` with a `title`; a row with several gathers them in `RowMenu`, and a page or workbench puts its secondary actions in `PageMenu` (both in `web/src/ui/ActionsMenu.tsx`). Menu items that open a dialog or ask for confirmation end with "…". An icon-only control is named by its `title`, which is also its tooltip, or by `aria-label` when it has no tooltip — never both. A value that does not exist yet is drawn as `Absent`.

A success toast confirms a command whose result is not visible where the reader is: a removal, a revocation, a sign-out elsewhere, work started in the background. A creation or edit that appears in place needs no toast. Every failure is a toast. A state that lasts while the page is open is an `Alert`. An empty region is an `Empty` that says what is missing and offers the way forward: the command itself when it is on the same page, a link when it is elsewhere. A loading region keeps its final shape. Irreversible actions ask first with `confirmDestructive`.

A dialog that collects input is a `FormDialog` (`web/src/ui/FormDialog.tsx`). The caller owns its trigger and `open` state; the dialog holds the `useAsyncAction` and hands it to the form inside, which mounts with each opening and so starts fresh; while it submits, the dialog cannot be dismissed. A dialog whose footer reads state of its own renders inside a `DialogSession`, and one that starts work as soon as a file is dropped has no footer. A secret shown once after it is created appears in `RevealOnceDialog`. Dialogs come in two widths, `default` and `wide`. Small descriptions under a field or link exist only when they change what the reader does or prevent a mistake; text that restates a label is left out.

All copy goes through Paraglide, including the kit's default labels, which live in `web/messages/ui/`. Messages are split by module (`web/messages/<module>/`), and a value joined with other text is one parameterised message, never fragments and punctuation put together in JSX. Messages speak in product words; `web/test/product-words.test.ts` keeps code identifiers out of them. Values are written in the current locale by one helper each: lists of like things with `formatList` (`web/src/ui/lists.ts`), numbers with `web/src/ui/numbers.ts` (counts, fixed decimals, percents), calendar days with `Day` and instants with `Timestamp` (`web/src/ui/Day.tsx`, `web/src/ui/Timestamp.tsx`).

## Adding or changing a component

A new component follows the same shape: a small set of props, styles block by block in its CSS, motion through the easing and duration tokens, and an implementation that renders the same markup on the server and in the first client frame. It exposes only what the workbench uses.

A change to the interface is done when `make check-web` passes, which runs the lint, the token, product-word and architecture checks and the tests; when it has been looked at in the light and dark schemes and at mobile width; and when every region it adds shows its pending, empty and error states where they apply.
