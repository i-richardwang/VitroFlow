# Interface

The workbench draws every control and surface from its own component layer in `web/src/ui/kit/`. Behavior comes from Base UI; each component is a `.tsx` file with, when it draws anything, a `.css` file whose classes start with `ui-`, and the CSS reads its type sizes, colors, radii, elevations and motion from the tokens in `web/src/styles/app.css` (a component's own geometry, such as a control's height, is written in its CSS). A few modules without markup (`floating.ts`, `refs.ts`, `mediaQuery.ts`, `clientValue.ts`, `motionToken.ts`, `dialogPresence.tsx`) are shared by the components. Component styles sit in the `components` cascade layer, so utility classes passed by a caller override them.

## Tokens and the page environment

`app.css` defines the only colors, type sizes, radii, elevations, durations, easing curves, breakpoints and stacking steps that exist; Tailwind's stock palette, type scale, radii, shadows, easings, breakpoints and animations are cleared. Colors are named by role: `fg` for text, `canvas`, `container` and `elevated` for the three backgrounds, `fill` laid over a background, `border`, `primary`, and the four status colors. The dark scheme redefines the same variables under the `dark` class, which follows the system preference and is set before the first paint. Fonts are the system stack.

The base layer is part of the design: components assume its resets (form controls inherit only family, size and line height; buttons keep their default padding; svg stays inline), the unitless body line height, and the focus ring on elements no component owns. A component whose look depends on the environment is fixed there, not with an override at its call site.

Code outside the kit uses semantic utilities (`text-fg-secondary`, `bg-fill-tertiary`, `border-border`) and never raw colors; secondary text is `text-fg-secondary` on the element that holds it. Drawings on the image canvas read the same variables (`var(--color-success)`), so marks follow the scheme, and series and treatments take `--color-chart-1` to `--color-chart-8` in order. Annotation class colors are the one exception: they are part of a model's data (`web/src/domain/models/classes.ts`), shared with server-side rendering and exports, so they are stored as hex values rather than tokens. Token names are always written out in full, never assembled from a variable, so a search for a token finds every use. `web/test/tokens.test.ts` holds the tokens to this: each is read somewhere, each variable read is declared, each color has its dark value, and no name is assembled.

Two widths change the layout: `--breakpoint-mobile` and `--breakpoint-laptop`. Stylesheets use both through Tailwind's variants; scripts read `--breakpoint-laptop` through `useIsCompact` (`web/src/ui/kit/mediaQuery.ts`), so the two never disagree.

## Pages

The signed-in frame is `Shell` (`web/src/ui/shell/Shell.tsx`). The sidebar sits on the canvas: the brand and the toggle on its top row, the places as one flat list of 36px rows, and the signed-in person at the bottom, whose menu leads to settings and signs out. While a settings page is open the sidebar holds the settings section instead, under a trail back home. Mod+B hides the sidebar entirely, its toggle moving to the start of the top bar, and a cookie the server reads remembers the choice. The page sits in one card with a full-strength border and no shadow, whose 44px top bar holds the breadcrumb and, at its end, the page's actions (`ShellActions`): every page's commands live there, at most one primary button followed by icons or a `PageMenu`. Pages outside it, sign-in and consent, sit in `AuthLayout`: one bordered surface inset from the viewport with the brand at the top, the language at the bottom and the content bare in the middle. Breadcrumbs come from each route's `staticData.crumbs`; on a phone the bar names only the page. The browser tab is named in the route's `head` by `documentTitle` (`web/src/ui/documentTitle.ts`), from the page's name or, for a page inside another, one parameterised message naming both.

A page is one of three kinds. `Page` (`web/src/ui/Page.tsx`) is a document in a reading column at most 960px wide and centered, or the card's full width when its content grows sideways with the data (`wide`, the experiment grid). A list leaves its name to the top bar; a page about one subject sets `headline` and opens with a `PageHeader`: the title (24px, 600), the subject's `status` right after it, a description and `meta` facts in chips. Sections, tables and panels follow, padded 24px from the card's sides (16px on a phone) and stacked 24px apart. `Workbench` (`web/src/ui/shell/Workbench.tsx`) is built around one framed subject and fills the card edge to edge: the subject on the left with its toolbars floating over it (`WorkbenchToolbar`), facts and display controls in a resizable inspector on the right (`WorkbenchInspector`, 360px by default, 300 to 600), which becomes a drawer on narrow screens. `SettingsPage` (`web/src/ui/Page.tsx`) holds the reader's own account, keys and connections and the workspace's people and machines: the top bar names it, and its content is a centered column at most 1024px wide of `SettingsGroup`s 36px apart.

A document page groups its content with `PageSection` (16px, 600, an optional description and an `extra` at the end of the heading row for a count or a small button) or, for a figure or a chart with its own header bar, a `Panel`. A page's figures are one `StatisticGroup` of `Statistic`s under the header: each a title over its value (24px, bold, tabular figures) and an optional line under it, together in one bordered panel. A workbench opens its inspector with `WorkbenchIdentity` (what the subject is) and groups the rest with `WorkbenchSection`, each ruled off from the next; it floats a lasting state over the subject with `WorkbenchAlert` and an empty subject with `WorkbenchEmpty`. A settings page groups with `SettingsGroup`, whose panel holds `SettingsRow`s, a table or a list. Pages declare what they contain; they do not write layout for the frame.

Surfaces on a page (`Card`, `Panel`) are a thin border on the container color, or a band of fill when they must weigh more; a settings group is a fill tray holding a bordered panel. Shadows belong to what floats over the page. Content that runs edge to edge, a table's header band or a list's hover fill, reaches the edges of the surface it sits on through `--surface-gutter` and insets its text by the same amount, so a table's first column and a list's names line up with the page title above them; each padded surface sets the gutter to its own padding.

A route with a loader shows `pendingComponent` in the shape the page will take, built from the skeleton parts next to what they stand for: `PageSkeleton` and its parts in the kit (`PageHeaderSkeleton`, `StatisticGroupSkeleton`, `TableSkeleton`, `ItemListSkeleton`, `SettingsGroupSkeleton`), `PageSectionSkeleton`, `SettingsPageSkeleton`, `PageColumnSkeleton` (the page's column), `WorkbenchSkeleton`, and a feature's own (`EpochChartsSkeleton`) beside its component. Skeletons are sized by the type scale and the components they imitate, never by pixels in a route.

## Composition

Controls and surfaces come from the kit. A feature never imitates one with `rounded-*`, `border`, `bg-*` and `shadow-*` utilities, and never overrides a component's internal height, radius or padding; it chooses a `size`, `variant` or `type`. Width, position and visibility belong to the outer layout. A missing component is added to the kit, not drawn in a route. `bun run architecture:check` rejects, outside the kit, stock breakpoints, `rounded-*` and `shadow-*`, raw lengths and colors in classes, and inline styles anywhere but the image viewport's drawings.

Things of the same kind look the same, and things of different kinds look different; the difference is carried by shape before color or size. One fact has one control: a status and the actions it allows are one menu, not a tag beside a row of buttons. A selection of one value is a `Select`, or a `ToggleGroup` when the few options should stay visible; a toggle is a `Switch`; a command is a `Button`. Things of one kind that are compared column by column are a `Table`; things that are each read on their own (models, machines) are an `ItemList` of `Item`s, one line each: the name with a tag or a `StatusDot` after it, then what sets the item apart and its facts at the end. Nothing in the workbench carries an avatar or an icon box. A dense data grid takes `Table size="small"`. A row with one action shows it as an `ActionIcon` with a `title`; a row with several gathers them in `RowMenu`, and a page or workbench puts its secondary actions in `PageMenu` (both in `web/src/ui/ActionsMenu.tsx`). Row actions sit in the table's `actions` cell or the item's `actions` and show while the row is hovered or focused. A name is set in the sans-serif at 500. Figures are sans-serif with tabular digits; monospaced type is only for code, keys and addresses. Text takes three colors: names in the text color, descriptive values secondary, dates, metadata and placeholders tertiary. Menu items that open a dialog or ask for confirmation end with "…"; one that downloads a file is a link (`href`). An icon-only control is named by its `title`, which is also its tooltip, or by `aria-label` when it has no tooltip — never both. A value that does not exist yet is drawn as `Absent`.

A success toast confirms a command whose result is not visible where the reader is: a removal, a revocation, a sign-out elsewhere, work started in the background. A creation or edit that appears in place needs no toast. Every failure is a toast, raised by `useAsyncAction` or, for work outside an action, by `runAction` (`web/src/ui/hooks/useAsyncAction.ts`). A state that lasts while the page is open is an `Alert`. A failure written on the page states the conclusion and the way out (Retry); the raw error goes in the `Alert`'s `detail`, folded away and copyable. An empty region is an `Empty` that says what is missing and offers one way forward: a command on the same page is a primary `Button`, and a way to another page is a default `Button` rendered as the link (`render`), never a bare text link. An empty table or list is replaced whole by its `empty`, header and all, and while it is empty the page or group does not offer the same command in its header. A loading region keeps its final shape. Irreversible actions ask first with `confirmDestructive`.

A dialog that collects input is a `FormDialog` (`web/src/ui/FormDialog.tsx`). The caller owns its trigger and `open` state; the feature's dialog holds its `useAsyncAction` and passes `busy`, and while busy the dialog cannot be dismissed. The form inside mounts with each opening and so starts fresh. A dialog whose footer reads state of its own renders inside a `DialogSession`, and one that starts work as soon as a file is dropped has no footer. A secret shown once after it is created appears in `RevealOnceDialog`, its values as `CopyableCode`, the read-only code block every copyable value takes. Dialogs come in two widths, `default` (520px) for a form in one column and `wide` (640px) for a table or a design laid out in two columns. Fields stack 16px apart; only a pair of short fields (a date and a number) shares a row, and related fields gather into a `Form.Group`, whose heading (14px, 600, ruled off from the fields) is the one way a dialog titles a section. Small descriptions under a field or link exist only when they change what the reader does or prevent a mistake; text that restates a label is left out.

All copy goes through Paraglide, including the kit's default labels, which live in `web/messages/ui/`. Messages are split by module (`web/messages/<module>/`), and a value joined with other text is one parameterised message, never fragments and punctuation put together in JSX. Messages speak in product words; `web/test/product-words.test.ts` keeps code identifiers out of them. Values are written in the current locale by one helper each: lists of like things with `formatList` (`web/src/ui/lists.ts`), numbers with `web/src/ui/numbers.ts` (counts, fixed decimals, percents), numbers inside a message by the message itself (a `number` declaration, never a pre-formatted string), calendar days with `Day` and instants with `Timestamp` (`web/src/ui/Day.tsx`, `web/src/ui/Timestamp.tsx`).

## Adding or changing a component

A new component follows the same shape: a small set of props, styles block by block in its CSS, motion through the easing and duration tokens, and an implementation that renders the same markup on the server and in the first client frame. It exposes only what the workbench uses.

A change to the interface is done when it passes `make check-web`; when it has been looked at in the light and dark schemes and at mobile width; and when every region it adds shows its pending, empty and error states where they apply.
